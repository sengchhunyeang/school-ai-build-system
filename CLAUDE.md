## What this is

A single-file, static HTML prototype of a school management system ("EduAdmin"), styled with Tailwind CSS (via CDN) and FontAwesome, with Chart.js loaded for future/partial use. There is no backend, no build step, and no package manager — `school_management_system.html` is the entire application.

## Commands

There is no build, lint, or test tooling in this repo. To work on it:

- **Run locally**: open `school_management_system.html` directly in a browser, or serve the directory with any static server (e.g. `npx serve .`).
- **Deploy**: Vercel serves the repo as static content; `vercel.json` rewrites `/` to `/school_management_system.html` so the file loads at the site root.

## Architecture

Everything lives in `school_management_system.html`, split into two parts:

1. **Static shell (top of `<body>`)**: sidebar, header, and a `<main id="mainContent">` container that all module views render into. Modal dialogs live at the bottom of the body, hidden via a `hidden` class and toggled with `openModal(id)` / `closeModal(id)`.
2. **Application script (bottom `<script>` block, ~line 372 on)**: a client-side, in-memory SPA with no persistence — all state resets on page reload.

Key pieces of the script:

- `currentRole` / `currentModule` — global state for which role is viewing the app and which module is active.
- `navModules` — array driving the sidebar nav; each entry declares which roles (`admin`, `teacher`, `student`, `parent`) can see it. `renderNavigation()` filters nav items by `currentRole`.
- `switchRole(role)` — swaps the active role, updates the header user badge, re-renders nav, and falls back to the `portal` module if the current module isn't allowed for the new role.
- `switchView(moduleId)` — clears `#mainContent` and dispatches to one `render*View(container)` function per module (`renderPortalView`, `renderAdmissionsView`, `renderStudentsView`, `renderTeachersView`, `renderAcademicView`, `renderFinanceView`, `renderCommunicationView`, `renderReportsView`, `renderSettingsView`). Each of these builds its section's HTML by injecting a template string into the passed container.
- Mock data arrays (e.g. `studentsData`) simulate a backend; form handlers like `handleAddStudent` mutate these arrays directly and call `showToast(...)` for feedback.
- `handleGenericSubmit(e, modalId, message)` is the catch-all handler for most modal forms that don't need custom logic — it just prevents default submit, closes the modal, and shows a success toast.

Because every module view is generated by string-templated `innerHTML`, adding or changing a feature within a module typically means editing its single `render*View` function rather than touching separate component files.

## Working conventions

- Keep everything self-contained in the one HTML file — no new dependencies/build steps unless the user asks for a project restructure.
- Follow the existing role-based visibility pattern (`roles: [...]` on `navModules`) when adding new modules or nav items.
- Follow the existing Tailwind utility-class style already used throughout (navy/emerald color scheme defined in the inline `tailwind.config`).
